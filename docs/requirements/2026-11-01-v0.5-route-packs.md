# 需求 v0.5 · 四条常见应用路线的完整开发流程与 Skill 装配

- 日期：2026-11-01
- 状态：`IMPLEMENTED_PENDING_REVIEW`
- 上游：v0.4 需求 [2026-11-01-v0.4-gap-closure.md](2026-11-01-v0.4-gap-closure.md)

## 背景

仓库已有 11 阶段生命周期、4 条路线 SOP 与 14 个候选 Skill，但缺少一个能回答以下问题的视图：**对 SaaS、企业自研、微信小程序、移动 APP 这四类最常见的应用，从开工到上线按什么顺序做、每一步用哪个 Skill、需要什么证据、哪一步没有回执就不能继续。**

现状的问题：

1. 路线知识分散在 `ROUTE_SOPS`（义务列表）、`PLATFORM_BRANCHES`（覆盖清单）与手写文档之间，没有阶段映射，也没有“开工前检查单”和“退出标准”。
2. 工作区只有 `route-sop.md`，回答不了“第 5 阶段该产出什么、由谁给证据”。
3. 文档与代码没有防漂移机制，平台 Gate 改一处，其他两处可能仍是旧值。

## 需求

| ID | 需求 | 验收方式 |
|---|---|---|
| R1 | 四条路线各有唯一 Route Pack，含开工前检查、11 阶段流程、Gate 阶段归属、负例与 Skill 侧重 | `validateRoutePacks()` 返回空；`test/route-packs.test.mjs` |
| R2 | 开工前检查是 PREFLIGHT，不得成为第 12 阶段 | `stageFlow` 必须等于 `STAGE_IDS`；校验断言 |
| R3 | Gate 文本不得复制，`gatePlan` 只引用 `ROUTE_SOPS` 下标并补阶段、证据与“不能替代” | `gatePlan` 长度等于 SOP Gate 数且下标一一对应 |
| R4 | Skill 不得复制或新增第 15 个；每个路线把 14 个 Skill 恰好划分为 core/strengthen/reference | 划分并集等于 `SKILL_IDS` 且互不重叠；core 含 implementation、verification、release-engineering |
| R5 | 路线包必须接入 catalog 校验 | `validateCatalog()` 包含 `validateRoutePacks()` |
| R6 | 工作区产出一份合并的路线包产物，状态 `DRAFT_NOT_EXECUTED` | `<slug>-route-pack.md`；产物计数 19 / 17 / 18 |
| R7 | CLI 可读取路线包 | `xeng route-pack [type] [--json]`；未知路线退出码 2 |
| R8 | `task --json` 必须带路线包 | JSON 含 `routePack.id` |
| R9 | 站点展示路线包，且不新增视图、页签或 DOM id | 「路线 SOP」页签内新增表格；`npm run check` 的 DOM id 列表不变 |
| R10 | 路线文档由代码生成，漂移即失败 | `npm run routes:docs` 重建；`npm run check` 逐字节比较 |
| R11 | 不得出现合规声明、平台回执或“已完成”措辞 | 生成文档断言不含“已满足/已合规”；证据默认 `NOT_RUN` |
| R12 | 不引入运行时依赖，不自动创建账号、备案、提审、部署或合并 | 零新增依赖；CLI 无网络调用；产物中显式声明不做这些动作 |

## 边界

- 始终做：一切内容映射到 11 阶段；Gate 文本单一真值；文档生成并校验漂移。
- 先问：是否需要新增顶层 Skill、是否需要拆分路线包为多个产物、是否需要新增站点视图。
- 绝不：把 PREFLIGHT 变成阶段、复制第三方 Skill 正文、声称满足法规、替用户提交平台动作。

## 验收顺序

1. `npm run routes:docs` 生成四份路线文档。
2. `npm run check` 通过（含 `validateRoutePacks()` 与文档漂移检查）。
3. `npm test` 全绿；`npm run verify`、`npm run build` 通过。
4. 站点 1440px 与 390px 截图复核路线页签与工作区新产物。

## 未验证项

- 路线包内容尚未在真实项目上验证；哪一条检查项无效或缺失需要真实项目反馈。
- 外部平台规则仍需逐条复核，本轮只记录 2026-11 观测结论。
